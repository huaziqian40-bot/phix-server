# 同步实时化 · 长轮询设计

> 生成:2026-09-29 · 状态:已上线
> 适用:phix 服务端、官网(网页端)、PH Launcher(PHL)、PH Launcher Lite(PHL Lite)、
> 心履(xinlv)服务端 · 心履 Windows / macOS / Android

---

## 0. 一句话

别的设备一改,**这边一个 RTT 就知道** —— 而不是等下一次定时轮询。

---

## 1. 为什么不是 WebSocket

用户最初的要求是"都用 WebSocket,这样零延迟"。结论是**长轮询**,理由如下。

两个生产服务端都是 **Waitress**(纯 WSGI)。WSGI 是"一个请求进、一个响应出"的模型,
**不支持 WebSocket**。要上 WS 得同时换掉:ASGI 服务器(uvicorn/daphne)+ Channels +
一个跨进程消息总线(Redis)+ systemd 单元 + Cloudflare 的配置。这些都要新引入依赖。

而在这个场景里,**长轮询和 WS 的延迟是一个 RTT,人眼分不出来**。因为同步的形态是
"**通知,然后自己去拉**":

    另一端改了 → 服务端说"变了" → 客户端跑一次正常同步(拉清单 + 拉对象)

服务端并不需要把数据推下来(数据是端到端加密的,服务端也推不了明文)。所以 WS
省下的那点握手/帧开销,在这里换不来任何可感知的差异 —— 却要付出换掉整个部署栈的代价。

**结论:在现有栈上零基础设施改动就能拿到"一个 RTT",那就用长轮询。**
如果将来要做"服务端主动推"(比如离线推送、多人协同),再上 WS / FCM,那时它才真的值。

## 2. 协议

### 2.1 phix(选课 / 账号 / 日程 / 课表 / 学校 / AI 配置)

    GET /api/v1/sync/watch?cursor=<上次拿到的光标>
    Authorization: Bearer <access_token>

响应:

```json
{ "ok": true, "changed": true,  "cursor": "3:2026-09-29T13:40:29.888817+00:00",
  "server_time": "...", "objects": [ { "name": "schedule", "revision": 2, ... } ] }
```

    { "ok": true, "changed": false, "cursor": "...", "server_time": "..." }        # 超时
    { "ok": true, "changed": false, "cursor": "...", "retry_after": 1.0 }          # 名额满了

`objects` 只在 `changed=true` 时带上 —— 省掉"醒了再单独问一次清单"的往返。

### 2.2 心履(心情记录)

    GET /api/v1/sync/watch/?since=<上次拿到的光标>
    Authorization: Bearer <ApiToken>

响应字段同上(`changed` / `cursor` / `server_time`,名额满时多一个 `retry_after`)。
心履这边 `changed=true` 只**发信号**,客户端随后自己调 `/api/v1/sync/pull/`。

### 2.3 光标(cursor)是什么

**不透明字符串**,客户端只负责原样回传,不许解析。服务端从**数据库现算**:

    光标 = "<对象条数(含墓碑)>:<最新一次 updated_at 的 ISO 时间>"

任何写入/删除都会把 `updated_at` 推到最新,所以光标必然变化;光标没变就说明这一轮
真的什么都没发生。

**为什么不记在进程内存里**:光标是这套机制的**正确性**基础。记在内存里的话,
换 worker、重启服务、多进程部署都会漏掉变化。进程内的 `Condition` 只用来"让变了
这件事能立刻叫醒等待的请求",**不做判断依据** —— 判断永远看库。

## 3. 三种回包必须分清(最容易写错的地方)

客户端拿到 `changed=false`,有两种**含义相反**的情况:

| 回包 | 含义 | 客户端该做什么 |
|---|---|---|
| `changed=true` | 云端真的变了 | 立刻同步一次,然后马上重挂 |
| `changed=false`,**没有** `retry_after` | 正常挂满 25 秒超时 | **立刻**再挂上(长轮询接力) |
| `changed=false`,**有** `retry_after` | 服务端挂起名额满了 | 先等 `retry_after` 秒,再挂 |

前两种在 HTTP 层**长得一模一样**,只能靠 `retry_after` 区分。

搞错的后果:

* 把"被打回"当"超时" → 客户端立刻重挂 → **热循环打服务器**,比不挂还糟;
* 把"超时"当"被打回" → 每次都要多睡几秒 → **秒级延迟就没了**。

所以 `retry_after` 这个字段**不能省**,客户端的循环里也**不能只看 `changed`**。

---

## 4. 挂起名额(为什么必须有上限)

**这是这套机制唯一会出事故的地方,必须理解。**

Waitress 是**线程池**模型:一个挂起的请求就**实打实占住一个线程**整整 25 秒。

假设线程池是 8,而有 8 个客户端挂在这里:

    8 个挂起 → 8 个线程全被占住 → 服务端再也接不了任何别的请求
             → 连"把数据写进去、好让长轮询醒过来"的那个写请求都进不来
             → 同步从"秒级"直接退化成"卡死"

也就是说:**没有上限的长轮询会饿死线程池,而且是自己饿死自己。**

所以两个数**必须成对配置**:

| 服务 | 线程数 | 挂起名额 | 配置位置 |
|---|---|---|---|
| phix | `--threads=24` | `PHIX_WATCH_SLOTS=6` | `deploy/deploy.py` 生成的 drop-in |
| 心履 | `--threads=32` | `MOODTREE_WATCH_SLOTS=8` | `run_server.bat` / Linux `xinlv.service` |

名额取"线程池的 1/4 左右",保证任何时候都留得下大部分线程干正事。

**拿不到名额就立刻返回** `{changed:false, retry_after:1}`,客户端退化成短轮询 ——
延迟仍然是秒级,但服务端活着。

**默认值取得很保守**(心履代码里默认 `2`,按 waitress 默认的 4 线程算),因为
取大了的后果是服务端卡死、取小了的后果只是客户端退化成短轮询 —— 两者严重程度
完全不对等,所以要往小的一边站。**单改一边就是上面那个事故。**

还名额必须放在 `finally` 里:客户端中途断开时 waitress 会抛异常打断挂起,
漏还几次名额之后长轮询就等于被永久关掉了。

## 5. 客户端侧的两个坑

### 5.1 读超时必须**大于**服务端的挂起时间

服务端挂 25 秒,客户端读超时必须给到 35~45 秒。

给短了会**在服务端刚要应答的那一刻自己把连接掐断** —— 表现是一串"看起来像长轮询、
其实一秒一次"的假失败。各处取值:

| 环节 | 超时 |
|---|---|
| phix/心履 服务端挂起 | 25s |
| PHL / PHL Lite 客户端读 | 35s |
| 官网转发(`PROXY_WATCH_TIMEOUT`) | 40s |
| 网页端浏览器读 | 45s |

### 5.2 自己刚写过的对象不算"变了"

用户每改一笔,写入会把光标推进 → 自己的长轮询立刻醒 → 白重读一次,
**编辑到一半的表单还会被刷掉**。

解法:服务端在 `changed=true` 的回包里带上清单(`name` + `revision`),客户端
**比对 revision,只重读真的变了的那些**。

### 5.3 前后台

* 网页端:切到后台就停(浏览器会节流后台请求,挂着只是白占服务端一个名额);
  切回前台再起。**不需要**特意补一次全量 —— 光标是拿库里的状态现算的,
  离开期间真有变化的话下一次长轮询会立刻返回 `changed=true`。
* Android:只在**前台**挂。后台进程里挂着的长连接会被系统杀掉,留着既白耗电又白
  耗流量,所以"仅前台"才是诚实的设计;回前台由 `onStart` 补跑一轮完整同步兜住。

## 7. 一个额外的并发陷阱(PHL)

接上长轮询之后,**有两处**会主动调 `sync()`:一秒一次的本地定时器和长轮询环路。
两者会撞上(你正在改文件、另一台设备同时也在改)。撞上时若各跑一轮,就会建出两个
同步引擎抢着写同一批文件和同一份 `state.json` —— 轻则白跑一轮,重则把同步状态写成
**过期的快照**,下一轮于是误判"本地变了"。

所以 `PhixSession.sync()` 加了**单飞护栏**:撞上时复用正在进行的那一轮,而不是排队
(排队等于把延迟叠起来,而秒级延迟正是这条链路存在的理由)。PHL Lite 那边本来就有
`RLock`,等价。

## 8. 实测数据

`_recon/verify_watch_live_e2e.py` 用**真账号**跑完整链路(真注册 → 真信封 → 真挂起)。

本机(直连,无 Cloudflare):

    真的挂住          25.0s
    另一端写入 → 唤醒  0.04s          ← 这就是延迟本身
    同时挂 7 条        1 条立刻拿到 retry_after,6 条正常挂满

线上(`--base https://phix.ing`,经 Cloudflare):

    真的挂住          26.5s
    另一端写入 → 唤醒  1.60 ~ 2.59s   ← 多出来的是 Cloudflare 的 RTT
    同时挂 7 条        1 条 2.7s 拿到 retry_after,6 条挂满 ~26s

对比改造之前:

| 端 | 改造前 | 改造后 |
|---|---|---|
| PHL | 每秒问一次(延迟 ~1s,但每秒一个请求) | 一个 RTT,空闲时零请求 |
| PHL Lite | **每 10 分钟**一轮 | 一个 RTT |
| 网页端 | **只有手动点刷新** | 一个 RTT |
| 心履(三端) | **只有手动/周期同步** | 一个 RTT(Android 仅前台) |

## 9. 排查

* **同步看起来"没生效"**:先看服务端是不是老代码 —— 查询串被丢掉了,光标对不上,
  会立刻返回。官网那层曾经就是这样(`_handle_proxy` 没透传 query)。
* **客户端在"短轮询"**:看回包里有没有 `retry_after`,有就说明**名额满了** ——
  要么调大名额,要么把线程数一起提上去(必须成对)。
* **一连串假失败**:客户端的读超时比服务端挂起时间短了。
* **改完模板/代码必须重启 waitress**:Django 模板是进程内缓存,不重启一直发旧的。
