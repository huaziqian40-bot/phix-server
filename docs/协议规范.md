## 0. 一句话

**phix** 是把「心履」和「PH Launcher / Pinghe Launcher Lite」打通的一套统一账号系统:
一套**用户名 + 密码**登录,**端到端加密**地把选课、账号、日程、课表、学校数据、AI 会话
在用户的多个设备之间同步。服务端**只存密文**,看不懂里面的任何内容。

## 2. 加密设计(必须先看这一节)

### 2.1 密钥链

> **两条链、两个盐,绝不能混**(2026-09-12 实测踩过:共用一个盐会导致
> 切「独立同步口令」之后**再也登不进来**)。

```
                            ┌─ 登录口令 P ─┐
                            │              │
              scrypt(P, auth_salt)     scrypt(P, kdf_salt)
                            │              │
                            ▼              ▼
                       MK(32B)          KEK(32B)   ← 只有 syncphrase 模式下
                            │              │         这里的 P 才是同步口令
             HKDF(MK,"auth")│              │ AES-256-GCM 解包
                            ▼              ▼
                 AuthHash(32B) ★      DEK(32B, 随机生成)
                            │              │  HKDF(DEK, "object-keys", <对象名>)
                    ★ 只有这一串            ▼
                      发给服务器        对象密钥(32B)
                    (服务器对它做          │ AES-256-GCM
                     PBKDF2 存起来)        ▼
                                      密文信封
```

| 名字 | 用途 | 什么时候变 |
|---|---|---|
| `auth_salt` | 派生 **AuthHash**(发给服务器的登录凭证) | **注册时定下,永不改变** |
| `kdf_salt` | 派生 **KEK**(包 DEK 的那把) | 换包裹口令时会变 |

**关键点一:服务器永远见不到口令。** 它只收到 `AuthHash = HKDF(scrypt(P, auth_salt), "auth")`。
HKDF 是单向的,所以**拿 AuthHash 反推不出口令,更算不出 KEK** ——
即使服务器被入侵、即使它记下了登录时收到的一切,也解不开用户云端的数据。

**关键点二:换密码不会让云端数据作废。** 对象密钥只由 DEK 派生;换密码只需在客户端
用旧口令解包 DEK、再用新口令重新包裹一次,`key_wrap` 换掉,**密文一个字节都不用动**。
(注意:**换登录密码必须同时换 AuthHash**;而切同步口令时登录口令没变,
AuthHash 就不该变 —— 这两条都有回归测试守着。)

### 2.1.1 两代 KDF

| `kdf_algo` | 派生方式 | 说明 |
|---|---|---|
| `scrypt-n15-r8-p1`(v1) | `KEK = scrypt(P, salt)`,服务器对比**口令原文** | 老账号兼容用。服务器相当于见过钥匙 |
| `scrypt-hkdf-v2`(v2,**新账号默认**) | 见上面的两条链 | 服务器永不见口令 |

服务端**两种都收**:客户端按 `/auth/keymaterial` 返回的 `kdf_algo` 决定发
`auth_hash` 还是 `password`。所以老账号不会被弄坏,新账号从注册那一刻起就是 v2。

### 2.2 两种模式(都支持)

| 模式 | `key_mode` | 包 DEK 的口令 | 服务端能否解密 |
|---|---|---|---|
| **简单**(默认) | `password` | 就是登录密码 | **v2 下不能**(它只有 AuthHash);v1 老账号理论上能 |
| **强**(可选) | `syncphrase` | 独立的「同步口令」,与登录密码不同 | **不能**,连实时都不能 |

- 两种模式下**服务端都不存明文密码、不存 DEK**,区别只在"服务端有没有机会见过用于派生
  KEK 的那个口令"。
- 切模式:客户端解包 DEK → 用另一口令重新包裹 → 上传新 `key_wrap` + `kdf_salt`。密文不动。

### 2.3 恢复码(重要,防"忘密码=数据全丢")

注册时生成一份 **恢复码**(24 个 base32 字符,一次性展示给用户保存),
服务端存**用恢复码派生的 KEK 包裹的同一把 DEK**(`recovery_wrap` + `recovery_salt`)。
忘记口令时用恢复码解包 DEK → 重设口令。

> 恢复码 = 数据的总钥匙。展示一次即可,永不落盘、永不上传明文。

### 2.4 精确参数(两端必须逐字节一致)

| 步骤 | 算法 | 参数 |
|---|---|---|
| KDF | scrypt | `N=32768 (2^15)`, `r=8`, `p=1`, `dklen=32`, `maxmem=64*1024*1024` |
| 对象密钥 | HKDF-SHA256 | `ikm=DEK`, `salt=b"phix/v1/object-keys"`, `info=UTF8(对象名)`, `len=32` |
| AuthHash | HKDF-SHA256 | `ikm=MK`, `salt=auth_salt`, `info=b"phix/v1/auth"`, `len=32` |
| KEK(v2) | HKDF-SHA256 | `ikm=MK`, `salt=kdf_salt`, `info=b"phix/v1/enc"`, `len=32` |
| 恢复码 KDF | scrypt | 同上,`salt=recovery_salt` |
| 加密 | AES-256-GCM | 随机 12 字节 nonce,密文尾部含 16 字节 tag |
| 编码 | base64url | **无填充**(`-`/`_`,去掉 `=`);JSON 里全部用字符串 |

**口令归一化**:取 UTF-8 字节前先做 NFKC 归一化 + 去掉首尾空白。两端都要做。

**两族 AAD**(为什么不是一个):

| AAD 族 | 值 | 用在哪 | 为什么 |
|---|---|---|---|
| 身份族 | `"phix/v1/identity|" + username` | `key_wrap`、`recovery_wrap`、`key_check` | 这三样在**注册之前**就要算好,那时 `user_id` 还不存在,只能用 username |
| 对象族 | `"phix/v1/object|" + user_id + "|" + 对象名 | 所有同步对象 | 同步发生在登录之后,`user_id` 已知;绑死"谁 + 哪个文件" |

> 身份族不绑 `user_id` 的代价:恶意服务端可以把 A 的 `key_wrap` 塞给 B。
> 但对象族绑了 `user_id`,B 拿到的 DEK 解不开 A 的对象、也解不开自己的对象,
> **立刻发现异常**,拿不到任何明文——只是拒绝服务,不是机密性破坏。

**信封格式**(一个字符串,便于存 JSON):

```
PHIX1.<b64url(nonce)>.<b64url(ciphertext||tag)>
```

**`key_wrap` / `recovery_wrap` / `key_check` 的信封**:同一格式,但 AAD 用**身份族**,
明文分别是 32 字节 DEK、32 字节 DEK、以及下面说的随机明文。

**密钥自检与「持有性证明」(重要)**:

`key_check` = 用 `key = HKDF(DEK, info="__keycheck__")`、身份族 AAD 加密**一串随机明文**,
密文由服务端保存;**明文 `key_check_plain` 只在注册接口被收下,此后任何接口都不下发**。

| 用途 | 做法 |
|---|---|
| 客户端自检「口令对不对」 | 解开 `key_check` → 解得开就是对的(GCM 认证标签保证),解不开就是错的 |
| 服务端校验「客户端真有 DEK」 | 客户端把 `key_check` 解出的明文 hex 作为 `dek_proof` 上报,服务端常量时间比对 |

> 为什么不能用固定常量:若明文是公开常量,任何人**照着填**就能通过
> "换密码 / 重新包裹 / 恢复码重置"的校验,等于没有证明。用服务端已知、
> 但只存在于密文里的随机明文,才真正要求"你得先解开它"。

**恢复码**:24 个 base32 字符(字母表去掉易混的 `I O 0 1`),展示为 `XXXX-XXXX-…`,
约 115 bit 熵。比对与派生前统一**去分隔符 + 转大写**。

> 实现参考:Python `hashlib.scrypt` + `cryptography`(AESGCM/HKDF);
> Node `crypto.scryptSync` + `crypto.hkdfSync` + `AES-256-GCM`。
> 三者都走 OpenSSL/RFC 标准,输出逐字节一致(已有互操作测试)。

### 2.5 威胁模型(诚实说明)

| 威胁 | 是否防住 |
|---|---|
| 服务端数据库/备份泄露 | ✅ 只有密文与密钥包裹,没有口令解不开 |
| 服务端被入侵后翻历史数据 | ✅ 同上(强模式下连实时都解不开) |
| 服务端实时偷看 | ✅ **v2 账号下防住了**:它只收到 AuthHash,HKDF 单向,推不出口令也算不出 KEK |
| 传输被窃听 | ✅ 部署后强制 HTTPS(Cloudflare);局域网阶段仅内网 |
| 对象被服务端张冠李戴 | ✅ AAD 绑定 `user_id` + 对象名,换文件就解不开 |
| 重放旧版本覆盖新版本 | ✅ 服务端 `revision` 单调递增 + 客户端 `base_revision` 乐观锁 |
| 用户忘记口令 | ✅ 恢复码 |

### 2.7 实现可以缓存 MK（**只影响速度，不影响协议**）

一次登录要派生两次 MK：一次算 AuthHash、一次解 DEK，而两次输入完全相同。
客户端**允许在进程内存里缓存 MK**（键 = 口令 + 盐 + scrypt 参数）：

- 只在内存，**绝不落盘**；进程退出即消失。
- 有上限（建议 8 条）与 TTL（建议 300 秒）。
- 登出 / 切换账号时**必须清掉**。
- 实测收益：本机登录客户端侧 **801 ms → 630 ms**（省 171 ms）。
- **线格式、密文、信封一个字节都不变**，两端各自实现都不影响互通。

## 3. 认证协议

基址:`https://<域名>/api/v1`(本地开发为 `http://127.0.0.1:8931/api/v1`)

除 `register` / `login` / `ping` 外,全部需要 `Authorization: Bearer <token>`。
所有请求/响应均为 JSON(`Content-Type: application/json; charset=utf-8`)。

### 3.1 `POST /auth/register`

```json
{ "username": "someone", "agree": true,
  "device": "家里的台式机", "key_mode": "password",
  "auth_hash": "<64 位 hex>",        // ★ v2：服务器只收这个，收不到口令
  "auth_salt": "<hex 32 字符>",
  "key_wrap": "PHIX1.…", "recovery_wrap": "PHIX1.…", "key_check": "PHIX1.…",
  "key_check_plain": "<64 位 hex,随机>",
  "kdf_salt": "<hex 32 字符>", "recovery_salt": "<hex 32 字符>",
  "kdf_algo": "scrypt-hkdf-v2" }
```

响应 `201`:

```json
{ "user_id": 12, "username": "someone", "token": "<40 位 hex>",
  "kdf_salt": "…", "auth_salt": "…", "recovery_salt": "…", "kdf_algo": "scrypt-hkdf-v2",
  "key_mode": "password", "key_wrap": "PHIX1.…", "recovery_wrap": "PHIX1.…",
  "key_check": "PHIX1.…", "key_version": 1 }
```

- 用户名只允许字母/数字/下划线/点/`@`/`+`/`-`/中文,≤150。
- **`key_wrap` / `key_check` / `key_check_plain` / `auth_hash` 等全部由客户端本地生成**,
  服务端只存不解析。**v2 账号下服务器从未见过用户的登录口令。**
- 服务端**不返回明文恢复码**——恢复码由客户端自己生成并展示给用户。
- 响应里**不含 `key_check_plain`**;此后的任何接口都不会再下发它。
- **老客户端**可以继续发 `"password": "……"`(v1 路径),服务端两种都收。

### 3.2 `POST /auth/login`

```json
{ "username": "someone", "auth_hash": "<64 位 hex>", "device": "笔记本" }
```

> v1 老账号发 `"password": "……"`。客户端先 `POST /auth/keymaterial {username}` 拿到
> `kdf_algo` 与 `auth_salt`,据此决定发哪种、以及用哪个盐算 AuthHash。

响应 `200`:`{user_id, username, token, kdf_salt, auth_salt, recovery_salt, kdf_algo, key_mode, key_wrap, recovery_wrap, key_check, key_version}`

- 令牌**长期有效**,按设备区分,可单独吊销。
- 失败:401 `{"error": {"code":"bad_credentials","message":"账号或密码不对"}}`
- 限流:同一 IP + 用户名,连续失败 5 次锁 5 分钟(429)。

> **`/auth/password`(换密码)、`/auth/rewrap`(切同步口令)、`/auth/recover`(恢复码重置)、
> `/auth/verify`(心履的服务间校验)同样接受 `auth_hash` 系列字段**:
> `old_auth_hash` / `new_auth_hash` / 直接 `auth_hash`。
> 换密码时要同时换 `new_auth_hash`;**切同步口令时 `auth_salt` 与 AuthHash 都不能变**
> (登录口令没变)。这两条都有回归测试(`devtools/test_authhash.py`)。

#### 3.2.1 服务端的"凭证代次护栏"

服务端存的是**发来的那串凭据的 PBKDF2 哈希**,它**不检查这串是口令原文还是 AuthHash**。
所以客户端漏发 `auth_hash` 时,服务端会默默把口令原文当凭证存下去 ——
**新旧密码与同步口令一起失效,而且整个过程不报任何错**(真发生过)。

为此三个会写凭证的接口都加了 `_credential_guard()`:

| 情况 | 服务端行为 |
|---|---|
| v2 账号 + `auth_hash` 系列字段 | 正常 |
| v1 老账号 + `password` 原文 | 正常(老路径,一直如此) |
| v2 账号 + `password` 原文 | **拒绝** `400 bad_request`,文案点名该补哪个字段(`old_auth_hash`/`new_auth_hash`/`auth_hash`) |

> 运维开关 `PHIX_V2_PLAINTEXT_OK`(环境变量,默认 `1`):设 `0` 时连
> "调用点自己允许原文"的场景也一律硬拒。等两端客户端都确认发 AuthHash 之后设 0 最稳。
> `/auth/verify` 是纯比对、不写任何东西,所以不带这个护栏(心履对 v1 账号仍需发原文)。

`/auth/recover` 是**唯一无法"柔和处理"**的一处:v2 账号的 AuthHash 由**登录口令**派生,
服务端没有口令、也绝不接触口令,所以**无法替用户重算** —— 只能硬拒,让客户端的报错浮出来。
(顺序上它排在 `dek_proof` 校验之后:恢复码不对的人先吃 401,不给他们探测凭证类型的机会。)

### 3.3 其它

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/auth/me` | 返回当前用户 + 全部密钥材料(供新设备解包) |
| POST | `/auth/logout` | 吊销**当前**令牌 |
| POST | `/auth/password` | `{old_password, new_password, key_wrap, kdf_salt, key_check, key_version}` — 换密码并把 DEK 重新包裹 |
| POST | `/auth/rewrap` | 只换 `key_wrap`(切简单/强模式、改同步口令) |
| POST | `/auth/recover` | `{username, recovery_code, new_password, key_wrap, kdf_salt, key_check}` — 用恢复码重设 |
| POST | `/auth/keymaterial` | `{username}` → 该账号的**公开**密钥材料（免认证；忘记密码时先取它才能用恢复码解 DEK）。账号不存在时返回**形状一致的假材料**，所以拿它枚举账号没有意义；限流 60 次/小时 |
| GET | `/auth/devices` | 列出本账号的令牌(设备名/最后使用时间) |
| POST | `/auth/devices/revoke` | `{token_id}` 或 `{all_except_current:true}` |
| GET | `/ping` | 免认证连通性探测 |

## 4. 同步协议

### 4.1 对象(object)

同步的最小单位是**一个具名对象**,内容是一段**密文信封**。服务端完全不理解内容。

**对象名规则**:`^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`,即字母数字开头,
可含 `.` `_` `:` `-`。名字会进 HKDF info 与 AAD,**改动即等于换密钥**。

### 4.2 清单

`GET /sync/manifest`

```json
{ "server_time": "2026-09-12T11:20:00+08:00",
  "quota": { "used_bytes": 812345, "limit_bytes": 209715200, "objects": 7, "limit_objects": 2000 },
  "objects": [
    { "name": "schedule", "revision": 4, "updated_at": "…+08:00",
      "size": 812, "sha256": "<密文的 sha256 hex>", "device": "家里的台式机",
      "deleted": false }
  ] }
```

### 4.3 取一个对象

`GET /sync/objects/<name>` → `{name, revision, updated_at, device, deleted, payload}`

- `payload` = 密文信封字符串;`deleted=true` 时 `payload` 为 `null`(墓碑)。

### 4.4 推一个对象(乐观锁)

`PUT /sync/objects/<name>`

```json
{ "base_revision": 4, "payload": "PHIX1.…", "device": "笔记本" }
```

- 成功 `200` → `{name, revision: 5, updated_at}`
- 冲突 `409` → `{"error":{"code":"revision_conflict"}, "current":{"revision":6,"updated_at":"…"}}`
  → 客户端必须**先拉最新、解密、与本地合并、再以新 revision 重推**。
- `base_revision: 0` = 新建;若已有对象则同样返回 409。

### 4.5 批量推送

`POST /sync/objects/batch`

```json
{ "objects": [ {"name":"schedule","base_revision":4,"payload":"PHIX1.…","device":"笔记本"}, … ] }
```

响应:`{ "results": [ {"name":"schedule","ok":true,"revision":5}, {"name":"timetable","ok":false,"code":"revision_conflict","current":{"revision":2}} ] }`
单项失败不影响其它项。

### 4.6 墓碑与历史

- 删除 = `PUT` 一个 `{deleted: true}` 的墓碑(revision 照常 +1),避免"删了又被别的设备同步回来"。
- 服务端保留每个对象最近 **10 个 revision** 的密文(便于回滚),更老的丢弃。
  `GET /sync/objects/<name>/revisions` 列出,`?rev=N` 取指定版本。

### 4.7 限额与错误

| 项 | 值 |
|---|---|
| 单对象密文上限 | 8 MiB |
| 每账号对象数 | 2000 |
| 每账号总字节 | 200 MiB |
| 单次批量 | 50 个对象 |

错误统一为 `{"error": {"code": "...", "message": "中文说明"}}`,
`code` ∈ `bad_request` / `unauthorized` / `bad_credentials` / `forbidden` /
`not_found` / `revision_conflict` / `quota_exceeded` / `payload_too_large` /
`rate_limited` / `server_error` / `name_invalid`。

| code | 什么时候用 |
|---|---|
| `bad_credentials` | **账号或密码不对**（登录、`/auth/verify`）→ 401 |
| `unauthorized` | **缺令牌 / 令牌无效或已吊销** → 401。客户端据此判断"要重新登录" |
| `forbidden` | 权限不足（比如 `/auth/verify` 的服务密钥不对）→ 403 |
| `payload_too_large` | 请求体或单个对象超过上限 → 413 |

> 这两个 401 要分清楚：**`bad_credentials` 是"你输错了"，`unauthorized` 是"你的登录失效了"**。
> 客户端对前者的处理是提示用户改密码，对后者是跳登录页 —— 混在一起用户体验会很差
> （2026-09-12 修：服务端原先两者都返回 `unauthorized`，与本节不一致）。

## 5. 同步哪些文件、怎么合并

**核心原则(来自 `云同步开发-交接文档.md` §7.2):本地 `data/` 永远是唯一真相源;
同步是"加在旁边"的一层,不许改成"以云为准"。**

### 5.1 一次同步的完整流程

```
1. 读本地 → 若距上次同步无变化则跳过
2. GET /sync/manifest                       拿远端 revision 表
3. 对每个对象:
   a. 远端 revision == 本地记录的已同步 revision → 只有本地改了 → 加密后 PUT(乐观锁)
   b. 只有远端改了                              → GET 密文 → 解密 → 合并进本地 → 原子写回
   c. 两边都改了                                → GET 密文 → 解密 → **客户端合并** →
                                                 加密 → PUT(base_revision=远端 revision)
   d. 409 冲突                                  → 重新走 c(最多重试 3 次)
4. 把同步状态写进 data/.sync/state.json
5. 有账号冲突 / 无法合并的 → 记进 state.json 的 conflicts[],由界面提示用户
```

### 5.2 同步状态文件(不进同步、不进备份包)

`data/.sync/state.json`(PLL/PHL 共用):

```json
{ "version": 1, "kind": "phix-sync-state",
  "server": "http://127.0.0.1:8931",
  "user_id": 12, "username": "someone",
  "last_sync_at": "…+08:00",
  "objects": { "schedule": { "revision": 5, "sha256": "…", "synced_at": "…" } },
  "conflicts": [] }
```

> **令牌与 DEK 不写这里**。令牌进各端自己的凭据存储(PLL 走 `data/secrets.json` 的
> DPAPI/文件加密,PLL/PHL 共用);DEK 只在内存里,靠 `key_wrap` + 口令每次解包。

## 6. 端到端加密对"本地共用"的影响

两个程序本来就在**同一台电脑、同一个 `data/`** 里共用数据。加了云同步之后:

- 同一台机器上,**先跑的那个程序负责同步**,后跑的那个看到的已经是合并后的本地文件
  (因为两个程序不能同时运行,天然不会打架)。
- 同步进程是"第三个写入者",必须遵守**同一条纪律**:
  **只在没有 `.phl-running` / `.pll-running` 运行标记时写**(交接文档 §7.6 推荐做法);
  若允许带锁写入,必须"读最新 → 合并 → 原子替换"。
- 本版本实现**保守方案**:检测到任一运行标记(心跳未过期)就跳过本轮同步,
  不抢写。用户手动点"立即同步"时也先检查。

## 7. 心履账号打通

心履(第一台服务器 `192.168.5.35`)是三端 + Web 的 Django 应用,有自己的用户表。
**不改它的数据、不迁它的库**,用"认证委托"打通:

```
用户在心履网页/客户端输入 phix 账号密码
        │
        ▼
心履 Django 自定义认证后端 core/phix_auth.py
        │  ① 先试本地 Django 账号(老用户照常)

        ▼

        │  成功 → 返回 {username, user_id}

心履自动创建/关联同名本地 Django 用户(set_unusable_password),
```

- `POST /auth/verify` 只对持有 `PHIX_SERVICE_KEY` 的服务端开放(常量时间比较),

- PLL/PHL 里配置的心履账号(`settings.yaml` 的 `accounts.xinlv`)因此可以和 phix 用**同一个账号名**。

### 9.2 两端实现必须注意的坑（移植时踩过）

1. **内部哨兵绝不能进 `conflicts`**：Python 的 `_MISSING` 是个 `object()`，
   一旦被写进状态文件，`json.dumps` 会抛 `TypeError` 让**整轮同步失败**。
   两端都必须把缺省值归一成 `null`。
2. **"没变化"也必须记基线**：如果一轮同步的结果是"本地已经和云端一样"，
   仍然要把 revision + 明文哈希写进状态文件。不记的话该对象的状态永远是空的，
   于是「本地改过没有」永远判成"改过" → **云端删除永远传播不过来**，
   而且每轮都要白拉一次密文再解密。
3. **两个盐不能混**：`auth_salt` 算 AuthHash（永不改变）、`kdf_salt` 包 DEK（会变）。
   混用会导致"切同步口令之后登录失败"。
4. **换登录密码必须同时换 AuthHash**；而切同步口令时 AuthHash **不能变**。
5. **AAD 里的路径要两端一致**：客户端拼 `/api/v1/...`，对象名**不能做百分号编码**
   （`agent:x` 编成 `agent%3Ax` 就会和服务端对不上，而且只在开加密后才暴露）。
6. **v2 账号绝不能发 `password` 原文**（`change_password` / `rewrap` / `recover` 三处都是）：
   服务端把"发来的第一串凭据"直接 `set_password()` 存下来，**它不检查你发的是哪一代**。
   漏发 `auth_hash` 的后果不是报错，而是**新旧密码与同步口令一起失效**（真发生过：
   PHL 移植版切同步口令时只发了 `{kdf_algo, auth_salt, key_mode}`）。
   服务端现在会拦（§3.3 的 `_credential_guard`），但客户端也该在测试里断言
   "请求体里没有口令明文"。

## 10. 应用层加密传输（可选，用它可以不依赖 HTTPS）

> 对应 `加密链路思路.md` §3 的要求：**三端之间全部走应用层加密，没有 HTTPS 也安全**。
> 实现：服务端 `api/e2e.py` + `api/middleware.py`；客户端 `phixcrypto` 的
> `seal_box / make_envelope / open_envelope_response`。

### 10.1 服务器密钥与发现

`GET /ping` 返回 `enc: 1` 与 `pk`（base64url，32 字节 X25519 公钥）。

**客户端必须把公钥固定下来**：首次信任后存到 `data/.sync/pinned/<host>.txt`；
以后对不上就**拒绝连接**并报 `server_key_changed` —— 防止有人在中间冒充服务器。
确认服务器确实换了钥匙后，删掉那个文件重新信任。

### 10.2 密封盒

```
seal_box(msg, recipient_pk):
    esk, epk = X25519 随机密钥对            # epk = 32 字节原始公钥
    shared   = X25519(esk, recipient_pk)
    salt     = epk || recipient_pk
    key      = HKDF-SHA256(ikm=shared, salt=salt, info=b"phix/v1/seal", len=32)
    nonce    = 12 字节随机
    ct       = AES-256-GCM(key, nonce, msg, aad=salt)     # ct 含 16 字节 tag
    输出      = epk(32) || nonce(12) || ct
```

### 10.3 请求 / 响应信封

```
请求：头 X-Phix-Enc: 1
      SK     = 32 字节随机（**每次请求换一把**）
      内层    = {"m":方法, "p":完整路径(含 /api/v1), "q":查询串, "b":请求体或 null,
                 "ts":unix 秒, "nonce":base64url(16 字节随机)}
      iv     = 12 字节随机
      ct     = AES-256-GCM(SK, iv, JSON(内层), aad = "phix/v1/req|" + 方法 + "|" + 完整路径)
      体     = {"sealed_sk": b64url(seal_box(SK, 服务器公钥)), "iv": …, "ct": …}

响应：头 X-Phix-Enc: 1
      体     = {"iv": …, "ct": …}      # 明文是原来的 JSON 响应体，AAD 与请求相同
```

- **查询串放在信封里的 `q`**，URL 上不带 `?` —— 这样 URL 里什么都不泄露。服务端会把它塞回 `QUERY_STRING`。
- **`p` 是完整路径**（服务端 `request.path` 就是它），AAD 里也是它 —— 所以把给 A 接口的信封发到 B 接口会被拒。
- **信封打不开时服务器回的是明文错误**（那时还没拿到 SK）。客户端必须**按内容判断**：
  响应体里有 `iv` 和 `ct` 才解密，否则当普通错误处理。

### 10.4 抗重放

- `|now - ts| ≤ 300` 秒。
- `nonce` 服务端维护 5 分钟 LRU，**重复即拒**。
- 两者都在密文里，网线上改不了。

### 10.5 兼容

**没有 `X-Phix-Enc` 头就完全走原来的明文路径。** 老客户端、`curl` 调试、
心履的服务间调用都不受影响。服务器不支持（`enc=0`）或探测失败时，客户端
**自动退回明文，绝不因此连不上**。

### 10.6 这一层解决了什么

| 场景 | 没有这一层 | 有这一层 |
|---|---|---|
| 局域网里有人嗅探 | 登录口令**明文可见** | 只有密文 |
| 服务器没接 HTTPS | 不敢用 | 照用 |
| 截获一次请求 | 可重放 | 一次性 SK + nonce，重放被拒 |
| 有人冒充服务器 | 看不出来 | 公钥固定，对不上就拒绝连接 |

> 注意：**这一层不替代"数据在云端的加密"**。前者保护"网线上怎么走"，后者保护"服务器上怎么存"。
> 两层是独立的，都要有。

## 12. 令牌体系：Ed25519 JWT + refresh 轮换

> 对应 `加密链路思路.md` §7、§8。实现：服务端 `api/tokens.py` + `api/models.py` 的
> `TokenSession` / `JtiBlacklist` + `views_auth` 的 `_issue_session` / `refresh`。
> 专项测试：`server/devtools/test_jwt.py`（52 项，本地与 `.41` 都跑）。

### 12.1 为什么要换

原来是 40 位 hex 的**长期不透明令牌**：偷到就能一直用，服务端只能靠查库才知道它还有效。

| 性质 | 长期不透明令牌 | 现在 |
|---|---|---|
| 有效期 | 无限（除非手动吊销） | **15 分钟**（`exp` 在签名里，改不了） |
| 验证方式 | 每次查库 | **本地验签**即可（业务机不用回连认证中心） |
| 撤销 | 删记录 | 会话表 + `jti` 黑名单，**实时生效** |
| 续期 | 不需要 | refresh **30 天**，**用一次换一次**，重放即撤销整个会话 |
| 被偷走 | 一直能用 | 15 分钟后自动作废；开了 DPoP 则离了客户端私钥根本用不了 |

### 12.2 两把服务器钥匙

| 钥匙 | 算法 | 文件 | 用途 |
|---|---|---|---|
| 传输加密钥 | X25519 | `e2e_key.txt`（600） | **保密**：网线上的信封（§10） |
| 令牌签名钥 | Ed25519 | `jwt_key.txt`（600） | **签名**：令牌真伪 |

两把是分开的：一把泄露不牵连另一把。公钥通过 `GET /auth/jwks` 发布（JWKS 格式，
免认证）—— 别的服务**只拿公钥**就能验签，不必共享密钥（设计文档 §7.1 方式 A）。
`kid` = 公钥 SHA-256 前 16 位，`/ping` 里也有，客户端可据此察觉"服务器换钥匙了"。

### 12.3 访问令牌长什么样

```
header  = {"alg":"EdDSA","typ":"JWT","kid":"<16 位 hex>", 可选 "jkt":"<DPoP公钥指纹>"}
payload = {"iss":"phix","aud":"phix","sub":"<user_id>","sid":"<会话id>",
           "iat":…,"exp":…,"jti":"<随机>","typ":"access","device":"…"}
```

- `sub` 用 **user_id**（用户名能改，id 不能）。
- `aud` 固定 `phix`，防止把令牌拿去别的服务用。
- 验签允许 ±`PHIX_JWT_LEEWAY`（默认 60）秒时钟余量。

### 12.4 会话与 refresh 令牌

**一次登录 = 一个 `TokenSession`**（一台设备一行）：

- `refresh_hash` 只存**摘要**（320 位随机串用 SHA-256 指纹；不是人选的密码，
  慢哈希没有意义，反而是查找时的性能灾难）。明文只在签发那一刻返回一次。
- **轮换**：`POST /auth/refresh` 成功后旧 refresh 作废、发一个新的。
  客户端**必须**把响应里的新 `refresh_token` 存下来。
- **宽限期**（默认 120 秒，`PHIX_REFRESH_GRACE`）：并发续期时两个请求可能手里都是同一个，
  这**不是攻击**。窗口内用旧的 → 200 + `rotated:false`，**不重发**新的那个。
- **窗口外用旧的 = 重放** → **撤销整个会话**（设计文档 §7 的原话）。
- refresh **不能**当访问令牌用（发业务请求一律 401）。

### 12.5 端点

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| POST | `/auth/refresh` | 免 | `{refresh_token}` → 新 access（+ 轮换后的 refresh） |
| GET | `/auth/jwks` | 免 | 签名公钥（JWKS） |
| POST | `/auth/introspect` | 服务密钥 | `{token}` → `{active, sub, sid, …}`（没有本地验签能力的服务用） |
| GET | `/auth/devices` | Bearer | 会话列表 + 老式令牌列表 + `access_ttl`/`refresh_ttl` |
| POST | `/auth/devices/revoke` | Bearer | `session_id` / `all_except_current` / `token_id` / `all_tokens` |
| POST | `/auth/login`、`/auth/register` | 免 | 响应里多了 `access_token`/`refresh_token`/`session_id`/`expires_*`；**`token` 兼容字段仍在**（`PHIX_LEGACY_TOKENS=0` 时不再发） |

错误码：**`token_expired`** 表示"该续期了"；其它 `unauthorized` 表示"该重新登录"
（会话被注销 / 令牌无效）。客户端据此分流。

### 12.6 DPoP（可选，令牌与客户端密钥绑定）

会话可以绑定客户端的一把 **Ed25519** 公钥（登录时带 `dpop_jkt` + 一个有效 `DPoP` 证明）：

```
头  DPoP: <证明 JWT>
证明头  {"typ":"dpop+jwk","alg":"EdDSA","jwk":{"kty":"OKP","crv":"Ed25519","x":…}}
证明载荷 {"htm":"GET","htu":"<完整URL或路径>","iat":<unix>,"jti":"<随机>"}
```

服务端校验：`htm`/`htu` 与本次请求一致、`iat` 在窗口内、`jti` 5 分钟内不重复、
且令牌头里的 `jkt` 与证明的公钥指纹一致（RFC 7638）。绑定后的会话**每个请求都要带证明**。

**不绑定也完全能用**（`jkt` 为空就不要求证明），所以这是"可选增强"。

### 12.7 实现注意

1. **注销要立刻生效**：会话状态在库里，请求时比对 —— 不能只依赖 JWT 自然过期。
2. **`token_expired` 与 `unauthorized` 必须分开**，否则客户端没法"自动续期"。
3. **宽限期机制不是"允许重放"**：它只覆盖并发续期（同一会话、几秒内），
   超出窗口一律按重放处理并撤销会话。
4. **`kid` 换了要能察觉**；客户端如果发现 `kid` 变了，应当提示（可能是服务器重装，
   也可能是有人在中间冒充 —— 与公钥固定的思路一致）。
5. 老式令牌在兼容期仍然有效，但**不要**把它当唯一凭据；两端升级完就设
   `PHIX_LEGACY_TOKENS=0`。
