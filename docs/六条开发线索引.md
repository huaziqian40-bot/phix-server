## 0. 怎么用这套东西

每条线都有两份文档，放在**那条线自己的仓库里**：

| 文档 | 作用 | 怎么用 |

| `docs\开发线提示词.md` | **给 agent 的启动指令** | 开一个新 agent 时，把 `---` 之间的内容整段发给它 |

提示词里已经写明了"先读哪些文档、遵守哪些约定、怎么验收、怎么发版"，
所以**只需要发提示词，不用另外解释背景**。

## 3. 跨线必须共同遵守的三件事

### ① 接口改动 = 改公共契约

改任何一个服务端接口，都要**同步更新对应的接口文档**，因为别的线照它实现：

- 改 phix 的接口 → 改 `D:\phix\server\docs\协议规范.md`（会影响 1、2、3、4、5、6）。
- 改心履服务端的接口 → 改 `D:\moodsite\web\docs\心履API文档.md`（会影响 3、4、6）。

### ② PHL 与 PHL Lite 之间有唯一的耦合点

两个程序**故意共用一份本地数据**（`settings.yaml`、`Schedule`、`Timetable`、`School`、
`agent/`），因此**不能同时运行**，用 `.phl-running` / `.pll-running` 标记 + 心跳来拦。

**那套磁盘格式与运行标记格式是两个产品之间唯一的接口**，
任何一边想改都要**两边一起改、同时发版**。详见 §2 的《共享数据与进程互斥》。

### ③ 长轮询的回包有三种，别搞混

`changed=false` 有两种**含义相反**的情况，在 HTTP 层长得一模一样：

| 回包 | 含义 | 客户端该做什么 |
|---|---|---|
| `changed=false`，**无** `retry_after` | 正常挂满约 25 秒超时 | **立刻**再挂（长轮询接力） |
| `changed=false`，**有** `retry_after` | 服务端同时挂起的名额满了 | **必须先等**再挂 |

把后者当前者处理 = **热循环打服务器**；把前者当后者处理 = **秒级延迟没了**。
另外客户端的**读超时必须大于服务端的挂起时间**（服务端 25 秒 → 客户端 35~45 秒）。

还有一个跨线的产品约定：**「检查更新」失败时只能显示"检查失败"，绝不能显示成"已是最新版本"。**
这两件事看起来像、意思完全相反 —— 把"没检查成"说成"已是最新"，用户会以为自己没落后。

## 4. 发版：六条线共用一套流程

产物、官网下载页、更新清单、GitHub Release 是**一套统一流程**，
各线**不要自己直接传服务器**（那会绕过一致性检查，曾经出过事故）。
相关脚本在 `D:\phix\_recon\`：

| 脚本 | 作用 |
|---|---|
| `publish_all.py` | 把各端产物搬到官网、更新下载页/校验表/夹具 |
| `update_download_page.py` | 更新下载页的版本号 / MB / 字节数 / 日期 / `checksums.txt` |
| `make_updates_manifest.py` | 生成 `updates.json`（更新清单） |
| `audit_release_local.py` | 发版前核对：产物内部版本、清单与实际文件、下载页三方一致 |
| `audit_about_all.py` | 核对各端「关于软件」是否齐全、失败态有没有被误报 |
| `release_all_v2.py` | 建 GitHub Release 并上传资产 |
| `verify_release_live.py` | 线上验收：清单 → 载荷下载校验 → 下载页 |
